Note — please read

This demo runs on synthetic data

Every company, person and sanctions entry on this site is invented. Nothing here is a finding about a real person or a real company, and no name shown is anyone's.

The pipeline itself is real. It reads the genuine Companies House and OpenSanctions publications in their native formats and runs against them unmodified — the demo corpus is generated in exactly those formats so every stage behaves identically.

Two reasons the public demo does not serve the real register:

  • Publishing inferences about real people. Entity resolution is probabilistic. At roughly 99.5% cluster precision a small share of merges is wrong, and a wrong merge here would assert that a named, living person is connected to sanctions. Publishing that carries real accuracy and data-protection obligations under UK GDPR that a demonstration should not take on.
  • Volume. The full register is about 5.6M companies and 12M filings — several gigabytes of working set and a serving index far beyond what a free-tier container can hold.

Using synthetic data also buys something real data cannot: the true answer is known by construction, which is the only way to measure recall — you can never see what blocking silently dropped.

What this is, in plain language

Companies have to declare who owns and controls them. Governments publish lists of people and companies under sanctions. In principle, checking whether a company is controlled by a sanctioned person should be a lookup.

In practice it is not, for one reason: the same person appears in different records under different spellings — "Dr Amara Piotr MacGregor" on one filing, "Amara MacGregor" on another, a transliterated version on a sanctions list. Nothing links them. And control is rarely direct: a sanctioned person owns a holding company, which owns another company, which owns the one you are looking at. Each filing on its own looks clean.

This tool does two things. It works out which records describe the same real person or company, and then it follows ownership upward through as many layers as it takes — so a link that is invisible in any single document becomes visible.

How to use it

1. Search a name
Type a company or person. Any known spelling works — the search looks at every variant a record used, not just the most common one. Results show a red flag if a sanctions link exists.
2. Open a result
You get the alias set (every spelling that resolved to this entity), who controls it, and how far up the chain any sanctioned party sits.
3. Read the ownership interval
Percentages appear as a range, like 37.5–75%, never a single number. Registries publish ownership in bands, so a two-step chain can only ever produce a range. Where a step grants control without a percentage — the right to appoint directors, for instance — you will see "control, no %" rather than a made-up figure.
4. Follow the chain
Each party in the path is clickable, so you can walk the structure yourself rather than trusting a single answer.

What it is good for

Sanctions and third-party screening, where the question is not "is this company listed" but "is anyone who controls it listed". Investigative research into opaque structures. Due diligence where a counterparty's ownership runs through several jurisdictions. And as a worked example of entity resolution — the demo corpus is synthetic, but the pipeline runs against the real UK Companies House and OpenSanctions publications.

Read this before believing a result. The public demo runs on a synthetic corpus built to look like the real registers. Names, companies and sanctions in it are invented. A hit here is a demonstration of the method, never a finding about a real person or company — and even on real data, an ownership link is a lead to verify against source filings, not a compliance decision.

Method

The pipeline is acquire → normalize → block → match → cluster → load, run offline; the service reads a flattened index built from its output.

Resolving records to entities

Comparing every record against every other is quadratic and impossible at register scale, so candidates are generated by blocking: 11 keys, unioned, each catching matches the others miss — phonetic name keys, sorted-token keys, name-plus-birth-year, registration number, address. Blocking sets the ceiling on what can ever be found, so it is measured in its own right rather than assumed.

Candidate pairs are then scored. Three matchers sit behind one interface: an interpretable additive log-odds model (the default, which reports a per-feature breakdown for every decision), a Fellegi–Sunter probabilistic model, and an LLM adjudicator. The LLM only ever sees the ~5% of pairs that fall between the accept and reject thresholds, which bounds both its cost and its blast radius, and makes its contribution measurable on its own.

Accepted pairs become connected components, which are then re-split where a component contains mutually exclusive attributes — two different birth years, three nationalities. Dual citizenship is tolerated; a third nationality is treated as evidence the cluster is wrong.

Two decisions that change the answer

Missing is not the same as different. When a record omits a field, that feature is scored as NULL, never as zero. "Both records state a nationality and they differ" is strong evidence against a match; "one record omits nationality" is no evidence at all. Collapsing the two teaches the model that missing implies non-match — and missingness is not random, so the resulting bias lands precisely on the cross-border records the pipeline exists to resolve.

Ownership is an interval, not a number. Registries publish bands. Multiplying midpoints down a chain yields a confident figure the source does not support, so the bounds are multiplied instead: 25–50% through 50–75% gives 12.5–37.5%. Where a step asserts control without a percentage, the arithmetic is abandoned and the path is flagged rather than guessed.

Following control

Traversal is bounded at six hops, and a path never revisits an entity. Both are necessary: corporate ownership graphs contain genuine cycles, some of them structures built deliberately to frustrate tracing, and an unbounded walk does not terminate usefully.

The downward closure from every sanctioned entity is computed once when the index is built, not per request, because it is the only query whose cost grows with graph depth rather than with the size of the answer. A test asserts that this precomputed answer matches a live traversal — if they ever disagree, the optimisation is a bug.

Accuracy, measured

Scored against a labelled ground truth on the fixture corpus: B-cubed F1 0.989 (precision 0.995, recall 0.984), pairwise precision 0.980 and recall 0.921, and blocking reduction ratio 0.9993. Recall within candidate pairs is 1.000 — every true match that survived blocking was found, which locates the remaining loss squarely in blocking rather than in matching.

Limits — what this cannot tell you
  • Roughly 5% of the real PSC register consists of statements rather than identified people ("no person has significant control"). Those are counted, never parsed into entities — an absence of owners in the data is not an absence of owners.
  • Where a chain terminates in a secrecy jurisdiction or a fiduciary layer, open data simply runs out. The tool marks this instead of presenting the last visible party as the ultimate owner.
  • Resolution is probabilistic. At 0.995 precision a small number of clusters are wrong, and a wrong merge creates an ownership link that does not exist.
  • Sanctions lists change constantly; this index is a snapshot, stamped with its build time below.
How it is served

The pipeline is batch and cannot run in a request path, so an offline step flattens the warehouse into a read-only index — entities with risk flags resolved, control edges re-pointed onto canonical ids, a denormalised name index, and the precomputed sanctions closure. The API reads that and nothing else; no matcher or clusterer is reachable from a request. The index ships inside the container image, so the whole service runs with no external database.

Measured on two shared vCPUs: p50 7.8 ms and p99 11.4 ms at one client, saturating near 225 requests per second, zero errors, ~0.7 s cold start. A load test runs in CI on every push and the build fails on a single error under load.
